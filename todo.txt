Everything below was measured on 2026-08-26 on one linux box (gcc 15.2.0,
C++20, RelWithDebInfo) against qxDOS at 7352fc5.  Where something could not be
measured here the entry says so.

- The local build still records no qxDOS commit, though CI now does.
.github/workflows/ci.yml pins QXDOS_REF and checks that commit out, so a CI run
says exactly which emu88 it compiled - but a developer's `make` still reads
whatever is in the sibling checkout at that moment.  EMU88_DIR is a plain
`CACHE PATH` with no version check and there is no submodule; the only qxDOS
SHA in the tree is docs/emu88-cpu-backend.md
citing f2392f0, and that is a 2026-06-04 validation note, not a pin.  qxDOS
does not test dosiz from its side either: its only workflow is release.yml,
which never mentions dosiz, and the only references to this project anywhere in
that tree are three descriptive comments - docs/hardware-roadmap.md:19,
emu88/audio_device.h:10 and emu88/dos_machine.h:86 - none of them a dependency
either side could act on.  So an emu88 change in qxDOS can break dosiz with
nothing on either side to catch it.
What is known today, and is written down nowhere else: with qxDOS clean at
7352fc5 ("IDIV: the non-faulting divider band is 8-bit only"), a full build and
`./tests/djgpp/run.sh` gives 42 passed, 0 failed, exit 0.  That is the whole of
the evidence that the pair is in sync.  Sibling precedent for the mechanism is
romwbw_emu, whose two workflows pin `CPMEMU_REF` to a SHA and check out cpmemu
beside themselves.

- `make test` runs zero tests and exits 0.  The Makefile's `test` target is `cd
$(BUILD_DIR) && ctest --output-on-failure`, and src/CMakeLists.txt contains no
add_test, no enable_testing and no include(CTest) - `grep -cE
'add_test|enable_testing|include\(CTest\)' src/CMakeLists.txt` is 0.  In a
fresh build directory ctest prints "No tests were found!!!" and returns 0, so
the target is a green no-op that reads as a passing suite.  The real suite is
tests/djgpp/run.sh, 42 checks, named in neither the Makefile nor README.md;
somebody has to already know it exists.  The smallest honest fix is to point
`make test` at run.sh; wiring the 42 checks into ctest individually is a bigger
change and buys parallelism nobody has asked for.

- a Crynwr packet driver installs itself on every single run, over a backend
hardcoded to return nothing, and prints two lines to stderr each time.
`./build/dosiz tests/HELLO.COM` emits "dosiz: ethernet/slirp backend
unavailable; INT 0x60 packet driver will accept guest calls but RX/TX will
no-op." and "dosiz: Crynwr pktdrv installed at INT 60h, stub at 0060:0000"
before the program's own output.  The install is unconditional - there is no
env gate anywhere (`grep -rn 'DOSIZ_PKTDRV\|DOSIZ_NET' src/` finds nothing) -
and the open it warns about is `ETHERNET_OpenConnection("slirp")`, whose only
definition is `{ return nullptr; }` in src/compat/dosbox_compat.cc.  So every
non-networking run pays two stderr lines and an INT 60h vector for a driver
that cannot move a packet.  56 lines of bridge.cc mention pktdrv.  It was not
always dead: a102726 "bridge: native virtual Crynwr packet driver at INT 0x60"
(2026-05-12, with follow-ups 5f10459 and 91eed4a) forwarded send and recv to
dosbox-staging's SLIRP backend, and the stub that returns nullptr is one of the
things 2691106 wrote when the DOSBox CPU went away - `git log -S
'ETHERNET_OpenConnection' -- src/` names exactly those two commits.  The
feature is documented nowhere: README.md, docs/ and CLAUDE.md have no hit for
"packet driver", "pktdrv" or "slirp", and WIP.md still lists networking under
"No plan".  Three ways out and the choice is the owner's: gate the install
behind an env var or a flag, silence the two messages and leave it installed,
or take it out until there is a backend to put under it.

- `--verbose` / `-v` traces nothing.  README.md and the program's own --help
string both say "--verbose, -v      Trace DOS syscalls".  src/dosiz.cc sets
cfg.verbose from the flag and reads it in exactly one place, to print that a
sidecar .cfg was loaded; `grep -c 'verbose' src/bridge.cc` is 0, so no syscall
path can see it.  Measured: `./build/dosiz -v tests/HELLO.COM` prints only
`dosiz-hello-ok` (plus the two pktdrv lines above), while `DOSIZ_TRACE=1
./build/dosiz tests/HELLO.COM` prints `[trace] AH=09` and `[trace] AH=4c`.  The
tracing the flag promises already exists under a different name.  Either wire
`-v` to set g_debug.trace, or delete the flag and the two lines of
documentation - but it is in the --help output, so today it misleads at the
terminal as well as on the page.

- two DOSIZ_* flags are parsed, documented as working, and read by nothing.
DOSIZ_CPU_TRACE is set into g_debug.cpu_trace in src/debug_settings.cpp and
appears nowhere else but its own declaration in debug_settings.hpp; its only
consumer was deleted by 2691106 "dosiz: run bridge.cc DOS host on emu88 via a
DOSBox CPU compat shim" (2026-06-05), which is visible as the removed line `if
(dosiz::g_debug.cpu_trace) {` in that diff.  It was a DOSBox facility (e62ac8a
"DPMI trace: force core=normal when DOSEMU_CPU_TRACE is set"), and emu88 is a
plain interpreter with no dynrec and no `core=` setting, so there is nothing
left for it to force.  DEBUGGING.md still documents it as logging every
instruction and forcing core=normal, cappable with DOSIZ_CPU_TRACE_LINES - a
name that does not appear anywhere in src/ - and docs/c-toolchain-guide.md
repeats the claim.  DOSIZ_DPMI_RING3 is the same shape: g_debug.dpmi_ring3 is
set and never read, because 6371618 "DPMI: default to ring-3 entry; legacy
ring-0 via DOSEMU_DPMI_RING0" (2026-04-23) inverted the switch and the live one
is now `want_ring3 = bits32 && !dosiz::g_debug.dpmi_ring0` in bridge.cc.
DEBUGGING.md still calls it "Required for DJGPP programs" and
tests/djgpp/run.sh has a note about it; all 42 run.sh checks and all 25
tests/DPMI_*.COM pass with no environment variables set at all.  Deleting both
members is a two-line change and the documentation is the real work.  A cpu
trace against emu88 would be a new feature rather than a repair, and it is
worth wanting; say so if it is.

(Sound Blaster) and a0f222b (joystick) all landed after it.  (2) is CLOSED:
"Text mode strips CR on write and expands LF to CRLF on read" had a true write
half and a read half that had been false for every disk file since 7463708;
the sentence now says disk reads are binary and only stdin is cooked, and the
CI step that asserted the opposite was corrected in the same commit.  (3) the
status table cites `dosiz mTCP-FTP.EXE -> prints usage
banner`, and `find . -iname '*mtcp*'` outside .git returns nothing - that
result cannot be reproduced from a clean checkout by anybody. (4) the same

`dosbox-staging/build/resources/drives/y/dos/xcopy.exe` and prints "SKIP:

- four files still describe emu88 as in-tree or vendored, and docs/CREDITS.md
claims it as dosiz's own code.  (There were five; the fifth was this file, and
this rewrite is what fixed it.)  The four: the header comment at the top of
src/CMakeLists.txt ("the in-tree **emu88** backend (vendored under ../emu88)"),
which its own body refutes 26 lines later, docs/CREDITS.md twice ("a
from-scratch x86 interpreter vendored into dosiz" and "source of the vendored
emu88 CPU core"), and patches/README.md ("dosiz runs on the in-tree emu88 386
core and has no build-time dependencies").  All were falsified by 8e507aa:
there is no emu88/ directory in this repository and the build fails to
configure without a qxDOS checkout, so patches/README.md's "no build-time
dependencies" is false twice over.  CREDITS.md is the worse of the two
problems, because it lists "the emu88 CPU core" among "dosiz's own code - ...
not derived from dosbox-staging", and CLAUDE.md says the opposite in as many

qxDOS/RIGHTS.md records emu88 as written for qxDOS, GPLv3-or-later, author

- DEBUGGING.md's last section tells the reader to patch a submodule that no
longer exists, using a JIT that never existed here.  It is headed
"Submodule-level hooks", points at `dosbox-staging/include/paging.h` and
`dosbox-staging/src/hardware/memory.cpp` for pinpoint memory watchpoints, and

- five DOSIZ_* environment variables ship undocumented and DEBUGGING.md's table
omits four more.  `grep -rhoE 'getenv\("DOSIZ[A-Z0-9_]*"' src/` yields
DOSIZ_AUDIO_DUMP, DOSIZ_BYPASS_EXTENDER, DOSIZ_CB_TRACE, DOSIZ_FRAME_DUMP,
DOSIZ_PATH, DOSIZ_SCREENSHOT_SECS and DOSIZ_VEC_TRACE.  Two of those seven are
in README.md - DOSIZ_FRAME_DUMP and DOSIZ_PATH - and the other five are in no
document at all.  DOSIZ_AUDIO_DUMP is not a debugging nicety - run.sh's
run_audio helper is built on it, and it is the only reason the ADLIB, SPEAKER
and SBDMA gates can assert anything without a sound card.  Separately,
src/debug_settings.cpp also defines DOSIZ_STACKWATCH, DOSIZ_4B_TRACE,
DOSIZ_4C_TRACE and DOSIZ_OPEN_TRACE, none of which appear in DEBUGGING.md's
table either.

- the AH=3F stale-ECX over-read logged UNCONFIRMED on 2026-05-19 is still the

- tests/djgpp/run.sh's run_one can pick a .asm source instead of the .COM on a
case-insensitive filesystem, and the sibling helper already guards against it.
run_one resolves its program with `ls tests/${name}.* | head -1`; run_audio
does the same glob and adds `| grep -iv '\.asm$'`, with a comment naming macOS
as the reason.  On a case-insensitive filesystem `ls tests/ADLIB.*` also
matches tests/adlib.asm, which is why that filter exists, and run_one lacks it
for EMS_PROBE, VCPI_PROBE, HMA_PROBE, JOYTEST and LFBTEST, each of which has a
lowercase .asm sibling.  This could not be tested here: this box is
case-sensitive, and under the C locale `.COM` sorts before `.asm` anyway, so
the ordering may well save it even on a Mac.  Flagged, not confirmed - it needs
somebody on macOS to run the suite once, or it needs the one-line filter copied
across on the grounds that it costs nothing.

- the build is not warning-clean and there is no -Werror gate.
src/CMakeLists.txt sets `-Wall -Wextra -Wno-unused-parameter` and nothing more.
A fresh build with SDL2 present emits 7 warnings; the same tree configured with
-DCMAKE_DISABLE_FIND_PACKAGE_SDL2=ON emits 9.  Both counts were measured here.
The seven: five -Wmisleading-indentation, one -Wunused-result, one
-Wclass-memaccess.  The extra two without SDL2 are -Wunused-function on
dosiz_video_key and dosiz_mouse_event, the two static hooks in bridge.cc's
anonymous namespace whose only callers sit behind #ifdef HAVE_SDL2 - genuinely
dead in that configuration, and the compiler is right.  Every site was read
here and every one is benign: the five indentation hits are all `if (a) x; if
(b) y;` clamps written on one line (mouse_to_virtual in bridge.cc, vesa_get in
video.cc, axis_count in hardware.cc); the fread reads two bytes into a `uint8_t
magic[2] = {0, 0}` and then compares them, so a short read cannot read
uninitialised memory; and the memset target VgaState is nothing but an int, a
uint8_t[256][3] and five uint8_t, non-trivial only because every member has a
default initialiser.  So this is hygiene, not a defect.  It is here because
warning-clean is the precondition for -Werror, and -Werror is the only thing
that stops the count growing.  qxDOS did the equivalent sweep for emu88 in
ad01cd0 "emu88: clear all 20 warnings, and stop hiding unused parameters".

- headless keyboard injection, the one thing WIP.md marked NEXT, was never
built.  The note reads "NEXT: keyboard-input injection with no interactive
session (scripted-keystroke dosiz feature?) to exercise st80's INT 16h path
end-to-end".  No such mechanism exists: grep of src/ for key_inject, DOSIZ_KEYS
and keystroke finds nothing, and no DOSIZ_* variable in debug_settings.cpp or
bridge.cc supplies scripted input.  It is the missing half of DOSIZ_FRAME_DUMP:
output can be asserted headlessly today and input cannot, which is what stops
the graphics fixtures above from becoming interactive tests rather than
one-shot renders.  It is a feature request, not a defect, and it is left here
so it is decided rather than drifted past.
